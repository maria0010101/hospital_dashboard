## 1. 專案概要

- **定位**：把 Python/Streamlit 版醫院業務儀表板改製為 Android 離線工具。使用者自行挑選手機中的「業務資料彙整-YYYYMMDD.xlsx」→ App 解析匯入內建 SQLite → 以 8 個分頁呈現各類營運指標，全部離線。
- **技術棧**：Kotlin + Jetpack Compose（Material 3）；自製輕量 xlsx 解析器（ZipFile + XmlPullParser，零第三方執行期依賴）；SQLite（`HospitalDb`）；圖表全以 Compose Canvas 自繪。
- **版本歷程（GitHub Releases）**：

## 2. 資料層盤點

### 2.1 xlsx 工作表 → SQLite 資料表（`SheetConfig.kt`）
| xlsx 工作表 | 資料表 | 重點欄位 / 處理 |
|---|---|---|
| 門診業務資料 | `outpatient_service` | 院區/科別/部別、初診/複診/聯醫初診、診次、門診人次、急診人次、收入 |
| 住院業務資料 | `inpatient_service` | 住院/出院人次、人日、部別/科別 |
| 病床別業務資料 | `bed_type_service` | 護理站、大類別(major_category)、病床類別(category)、登記/實開床數、人日、佔床率（**1150826 起 24 欄，移除樓層/科別**） |
| 院外門診部服務量 | `offsite_clinic_service` | 醫療/保健門診 |
| 會計室報表資料 | `accounting_report` | 洗腎、健檢（門診/住院）等 |
| 其他營運管理指標資料 | `ops_management_indicators` | 手術（門診/住院）、生產、總收入/自費收入（門診/住院） |
| 醫師服務量 | `physician_service` | 醫師代碼/姓名、部別/科別、診次、人次、人日、收入（derive：ym→year/month） |

- 匯入（`HospitalDb.importWorkbook`）：每表 DROP→CREATE→INSERT，單一交易失敗自動回滾；「更換」＝重新走選檔流程。
- **共用查詢架構（DashboardRepo）**：
  - `Filters`（年度/月份/院區/部別/科別 + showYoy）；`whereFor(filters, withDept, yearOffset)` 產出 WHERE 與參數（offset=-1 為去年區間）。
  - **錨點月**：篩選範圍內最新月（`anchorYm`）；近三個月 `monthBack`；YoY 用去年同月（圖表上以「(去年)」虛線序列呈現）。
  - 病床支援「**僅最新年月 / 累計**」雙模式：`bedLatestYm` + `ymCond`（latestOnly）影響 bedBranchOcc / bedBranchRegVsOpen / bedPivot / bedYoyCompare / bedDetail 及其去年同月錨定。
  - 特殊防護：`avgCast`（佔床率欄位含 `#DIV/0!` 字串）、單字元/符號名稱排除（混淆字典）。
- **樣本資料與混淆**：原始混淆工具 `make_sample.py`（本機 `/home/hpd/文件/hospital_dashboard/樣本資料/`）；repo 內 sample_data 現況為使用者網頁版 `sample_data-1150826.xlsx`（5.39MB，與工具產出 4.87MB 有差異），混淆對照表僅存本機不外流。混淆涵蓋：院區(甲/乙/丙)、部別、科別、醫師、門診部、護理站(01..49)、大類別(01..06)、病床類別(01..13)；數值採院區倍率縮放，比率欄位不動。

## 3. UI 架構

- 狀態機（`MainActivity` + `DashboardViewModel`）：`Loading → NoData(FilePickScreen) → Importing → Ready(DashboardScreen)`；匯入失敗 ImportError。
- `DashboardViewModel` 持有：`filters`、`tabIndex`（放大檢視返回原分頁用）、`zoomChart`（全螢幕放大內容）、AI 引擎設定/混淆對照表。
- 通用 UI 結構：TopAppBar（資料更新日期、⚙ 篩選、🔄 更換）→ **KPI 列**（最新月＋去年同期，點擊開各院區單月明細）→ **分頁列（8 分頁）** → 分頁內容垂直捲動。
- 篩選面板（FilterSheet）：年度（至少一）、月份/院區/部別/科別（全選可展開細項、空選=全選）、YoY 開關、重設=近三年。

## 7. 已知限制與技術債（規劃輸入）
1. **版本命名落差**：Release tag 0.5 內為 versionName 0.4.1；tag 與 in-app 字串未對齊（使用者命名習慣 v0.x tag vs 0.x 版號混用）。
2. **Release 流程受限**：repo 規則＝發布即 immutable、tag 建立僅網頁可為（擁有者）→ 只能「草稿上傳資產→網頁發布」；已寫入操作 SOP（見 §9）。
3. **樣本資料狀態分歧**：repo 內 sample_data-1150826.xlsx 為使用者網頁上傳版（5.39MB），與 `make_sample.py` 產出（4.87MB）內容可能不同步；工具腳本已不在 repo（被刪除），僅存本機。
4. 無自動化測試（僅 stub）、驗證依賴人工 adb；大量「放大後互動路徑」尚未逐一自動驗證。
5. 真實資料長駐手機；公開畫面需用樣本資料避免外洩（截圖已用樣本）。
6. 工具鏈備忘：android-studio 終端對 heredoc（`<<`）會掛，用「寫檔＋`python3 /tmp/x.py`」執行；GitHub API token 由 `git credential fill` 取得，不可輸出/入參數。
7. KPI 行與部分橫條的端值、長條圖在極短/極長條的標籤省略策略屬「有條件顯示」（寬度防溢出），規劃時留意。
8. AI 分頁需外部引擎（Ollama 192.168.1.50:11434 等），離線環境僅 UI 可用。

## 9. 操作 SOP 備忘（Release）
1. 升版：`app/build.gradle.kts` versionName/versionCode → commit → push main。
2. `./gradlew :app:assembleRelease` → 驗證（apksigner/aapt badging）→ 複製到 `/home/hpd/文件/hospital_dashboard/`。
3. 以 API 建 **draft**（tag_name＝目標版本，draft:true）→ 上傳 APK 資產（uploads.github.com）→ 填 body。
4. 網頁端由使用者 **Publish**（API publish 會因規則擋 tag 建立；網頁可）。
5. 驗證：GET releases 檢查 tag/assets/下載連結。
